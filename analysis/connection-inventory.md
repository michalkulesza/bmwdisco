# BimmerLight iOS connection inventory (v3.8 build 54)

## Scope and confidence

This is a static inventory of the extracted `com.bimmerlight.prod-3.8-eeveedecrypter/Payload/BimmerLight.app` and the existing `analysis/*strings.txt`, `*symbols.txt`, and `*exports.txt` dumps. The quoted offsets are anchors in those generated dumps; they are not source line numbers from the original Swift files. Strings and exported symbol names establish that code and UI surfaces are present, but by themselves do not prove a particular path ran. The app-facing instructions below are corroborated by embedded localization strings; transport/control details remain static evidence only.

## Declared iOS capabilities

`Payload/BimmerLight.app/Info.plist` is a binary plist (so it has no useful text line numbers). `CFBundleIdentifier=com.bimmerlight.prod`, `CFBundleShortVersionString=3.8`, `CFBundleVersion=54`. It declares `NSBluetoothAlwaysUsageDescription` (“…Bluetooth to connect to external devices…”), `NSBluetoothPeripheralUsageDescription` (“…communicate with…nearby accessories”), and `NSLocalNetworkUsageDescription` (“…devices on your local network…”). `UIBackgroundModes` includes `bluetooth-central` and `external-accessory`; `UISupportedExternalAccessoryProtocols` includes `com.obdlink`. No `NSBonjourServices` entry was present.

## Supported transport/adapters surfaced in the binary

The `EdiabasKit` `CommunicationInterfaceType` enum exports distinct cases for Bluetooth adapters and network adapters. See `analysis/EdiabasKit.exports.txt:1611-1625` (each exported case), with readable case names in `analysis/EdiabasKit.strings.txt:465-479` and `analysis/EdiabasKit.strings.txt:377-395`.

- Bluetooth cases: UniCarScan, OBDLink, OBDLink MX, Konnwei, vLinker, Vgate iCar, Veepeak, and BimmerCommander.
- Network cases: HSFZ, THOR, Wi-Fi, BM3, MHD, modBM, and vLinker Network.
- Service classes include per-vendor Bluetooth implementations plus `BluetoothServiceBase` / `IsoTpBluetoothServiceBase`, `OBDLinkEAService`, and `HSFZNetworkService`, `ThorNetworkService`, `VlinkerNetworkService`, and `NetworkServiceBase` (`EdiabasKit.strings.txt:377-400`).
- ELM is mentioned as an `ELMBluetoothService` resolver (`EdiabasKit.strings.txt:1020`), but there is no ELM case in the exported `CommunicationInterfaceType` cases at `EdiabasKit.exports.txt:1611-1625`; its shipped/UI support status is unresolved.

The app's English localization states that E-series supports Bluetooth and not ENET/Wi-Fi, while F/G-series supports most adapters including ENET/Wi-Fi (`analysis/BimmerLight.strings.txt:1598-1603`). It names specific Wi-Fi/ENET options including ENET cable/Wi-Fi, UniCarScan, vLinker Wi-Fi, BM3, MHD Universal, modBM ENET, xHP, THOR, KIES Wi-Fi, and MG Flasher (`analysis/BimmerLight.strings.txt:1481-1482`). The same localization says standard adapters can be too slow for strobe-style flashing (`analysis/BimmerLight.strings.txt:1592`); this is a product/UI claim, not measured performance here.

## Connection flow indicated by the evidence

1. User-facing setup instructions say to plug an adapter into the OBD-II port, turn on ignition (engine need not run), enable diagnostic mode on G-series by pressing Start three times, then choose an adapter and tap Connect. The UI says the app detects the vehicle and its lighting modules (`analysis/BimmerLight.strings.txt:1473`, with the instruction “choose your adapter, and tap Connect” at `analysis/BimmerLight.strings.txt:1473-1474`).
2. BLE code uses CoreBluetooth and contains service discovery, characteristic selection, notification/read/write paths, and BLE restoration/reconnect strings (`analysis/EdiabasKit.strings.txt:670-757`). Examples: OBD-like advertisements at `:683`, restoration at `:687`, and checks for readable/notifiable and writable characteristics at `:694-696` and `:738`. This supports a BLE discovery/transport design. The follow-up instruction pass recovered short hex-like literals and two full UUID strings; see “Decoded adapter constants” below. Config metadata names `targetWriteUUIDs` and `targetNotifyUUIDs` (`analysis/EdiabasKit.strings.txt:1609-1610`), but this pass does not assign any literal to a service/write/notify role.
3. External Accessory support is specifically present for OBDLink: the plist protocol is `com.obdlink`; the binary imports ExternalAccessory and has `OBDLinkEAService` with connect/sendRequest/stream methods (`analysis/EdiabasKit.strings.txt:73`, `analysis/EdiabasKit.exports.txt:224-230`). Strings include accessory waiting, writes and disconnects (`analysis/EdiabasKit.strings.txt:788-795`). This is a separate accessory path from BLE.
4. Network services expose `connectTo(ip:port:)`, connection state, and byte request methods (`analysis/EdiabasKit.strings.txt:852-883`; `analysis/EdiabasKit.exports.txt:267-277,308-316`). The vLinker service has log strings for `192.168.0.10:` while the port is appended dynamically (`analysis/EdiabasKit.strings.txt:852-853`); no concrete port number is established by that text. HSFZ detection also has `sendBroadcastMessage()` and a detection timeout (`analysis/EdiabasKit.strings.txt:799-814`). Do not infer a particular IP/port for all network adapters from the vLinker log.
5. A saved-vehicle connection path appears to try remembered vehicles, then detect on failure/stall (`analysis/EdiabasKit.strings.txt:871-874`). There are named operations for vehicle detection, reading VIN/vehicle information, ECU/module scans, and setting a diagnostic interface (`analysis/EdiabasKit.exports.txt:1105-1108,1245-1250,1298-1315`; scan status strings at `analysis/EdiabasKit.strings.txt:809-815,1248-1253`). These names support the apparent sequence but do not by themselves prove a strict runtime order.
6. The command path has an `ExecuteLightServiceImpl`, a `DiagnosticTransport` singleton with `setInterface`, and communication-service `sendRequest` interfaces (`analysis/EdiabasKit.exports.txt:1074-1108,348-353`). Bluetooth sends include `sendUdsPayload` (`analysis/EdiabasKit.exports.txt:199-201`), and `EdiabasKit` strings name `execute(steps:stopOnError:)`, `sendEngineActuation`, and `sendEngineRead` (`analysis/EdiabasKit.strings.txt:1083,1129,1138`). A defensible static model is: selected communication service → diagnostic request/UDS transport → light action steps. Which exact byte payload is sent for a given UI action requires following the relevant action pack and function/data flow, beyond this inventory.

## Preconditions, warnings, and recovery surfaced to users

- Connection helper: “Turn on the ignition (the engine doesn't need to be running)” and G-series diagnostic mode via three Start presses (`analysis/BimmerLight.strings.txt:1473`). The status prompt advises checking ignition and adapter availability (`:1624-1625`).
- Adapter/UI warnings: “No OBD accessory found. Please connect your adapter” and unsupported accessory protocol (`analysis/EdiabasKit.strings.txt:1300-1302`); Bluetooth errors say to enable Bluetooth, reconnect/unplug-replug the adapter, or check permission (`analysis/EdiabasKit.strings.txt:1321-1328`).
- Network errors include network off, unauthorized, unsupported, timeout and connection failure (`analysis/EdiabasKit.strings.txt:1305-1311` and error enum names in `analysis/BimmerLight.strings.txt:18634-18648`).
- Safety/preconditions: “Vehicle must be stationary for headlight actions” (`analysis/EdiabasKit.strings.txt:1304`); the FAQ says later-generation modules stop responding to diagnostic commands above about 5 km/h (`analysis/BimmerLight.strings.txt:1424`). Setup/help also says the app is for show/demo use, not public roads, and tells users to unplug the OBD adapter when not in use (`analysis/BimmerLight.strings.txt:1507` and adjacent help text).
- Recovery: after a lost connection, help text says the app tries to reconnect; if that fails, reconnect the adapter, ensure ignition is on, and manually reconnect (`analysis/BimmerLight.strings.txt:1407-1408`).

## What remains unproven

This pass inspected only focused initializer/callback instructions in addition to the string and export dumps. The full UUID roles and any standard expansion of the short UUID-like tokens remain unassigned; concrete network ports, runtime adapter dispatch, diagnostic-mode enforcement, and exact ECU request/response bytes for a selected light action remain open. The app was not run and no vehicle was connected. ELM support remains ambiguous: a resolver name exists but no corresponding public interface case was found in the inspected export list.




## Decoded adapter constants (static instruction follow-up)

`analysis/adapter-constants.txt` is generated by `analysis/adapter-constants.py` from ARM64 MOVZ/MOVK sequences in once-initializer function ranges. It recovers these byte strings alongside adapter-name fragments: BimmerCommander `FFF2` at function VA `0x18570:0x185e4` and `FFF1` at `0x18674`; Konnwei `FFF2`/`FFF1` at `0x18330`/`0x183c0`; Veepeak `FFF2`/`FFF1` at `0x1892c`/`0x189bc`; vLinker `2AF1`/`2AF0` at `0x17f0c`/`0x17fe0`; and Vgate iCar `2AF0` at `0x18bc4`. The functions also construct their vendor-name fragments (`BimmerCommander`, `Konnwei`, `OBDLink`, `Vlinker`, `UniCarScan`, `Veepeak`, `VgateIcar`). These are literal candidates in functions whose service constructors copy static adapter configs; field assignment and UUID semantics are still unproven. Raw words and decoding are in the generated output by adapter section.

The binary also contains two full UUID strings: `E7810A71-73AE-499D-8C15-FAA9AEF0C3F2` at `analysis/EdiabasKit.strings.txt:746` and `BEF8D6C9-9C21-4C9E-B632-BD58C1009F9F` at `:666`. Both have code references from function `0x1e65c` (`analysis/EdiabasKit.references.txt:1115-1116`). The output preserves this shared reference, but this pass does not identify which UUID is the service or which are characteristics.

ELM-style command literals include `ATPBC101`, `ATSPB`, `ATAT2`, `ATCAF0`, `ATPBE101`, `ATST10`, `ATFCSH6F1`, and `ATSH6F1` (`analysis/EdiabasKit.strings.txt:2409-2450`). Direct references tie `ATPC` and `ATZ` to functions in the `BluetoothServiceBase.swift` image range (`analysis/EdiabasKit.references.txt:1271,1282,1290`) and `ATZ` to the OBDLink External Accessory path, next to `performAdapterConfiguration()` (`analysis/EdiabasKit.references.txt:2148-2149`; source path literal at `analysis/EdiabasKit.strings.txt:769`). The static string groups do not establish a complete per-adapter initialization sequence.
