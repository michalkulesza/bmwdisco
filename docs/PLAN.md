## Adapters

All three speak UDS to F-series (D-CAN / Ethernet).

| Adapter    | Transport                       | Framing                                                                                                                                                                            | Notes                                                                                                                          |
| ---------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| ENET       | TCP 6801 (USB-C Ethernet)       | HSFZ: `len(4 BE) 00 01 F4 <ecu> <UDS>`; answer alive-check 0x12 with 0x13; type 2 = ACK                                                                                            | Discovery: UDP broadcast `169.254.255.255:6811` implemented but PARKED (fails on the car, see uncertainties); manual IP works. |
| Thor       | TCP 23 over the adapter's Wi-Fi | BMW-FAST `80                                                                                                                                                                       | len, dest, src F1, payload, additive checksum`; echo filtering                                                                 | Firmware behaviour unverified. |
| Vgate iCar | BLE ELM327                      | Init `ATZ ATE0 ATS0 ATL0 ATH1 ATAL ATCAF0 ATPBE101 ATSPB ATBI ATAT2 ATFCSH6F1 ATSH6F1`; per-ECU `ATFCSD<ecu>30FF08 ATFCSM1 ATCRA6<ecu> ATCEA<ecu>`; ISO-TP SF/FF/CF + flow control | Write char `BEF8D6C9-9C21-4C9E-B632-BD58C1009F9F`; slower round-trip — warn on fast presets.                                   |
| Demo       | in-process simulator            | —                                                                                                                                                                                  | Any F chassis, fault injection.                                                                                                |

Platform split (2026-10-15): iOS keeps **ENET / Thor / Vgate iCar / Demo**. Android additionally lists **ELM327 Bluetooth Classic / ELM327 Wi-Fi / USB K+DCAN**. Android ELM links use D-CAN mode 2 (`ATI` twice, `ATD`, `ATPB C101`, extended addressing with CAF1 for short requests and CAF0 for long requests); the legacy ELM command sequence above remains the iOS default. Classic uses paired RFCOMM SPP, Wi-Fi ELM defaults to `192.168.0.10:35000`, USB K+DCAN uses BMW-FAST over 115200/8N1. Fresh Android THOR settings default to `192.168.4.1:23`; iOS and already saved hosts are preserved. See [Android connection notes and device checklist](android-connection-notes.md). Android native compilation and real-adapter validation remain pending.

## Architecture

```
app/                      expo-router routes (thin; compose feature components)
src/
  transport/              TCP (ENET, Thor, ELM Wi-Fi), BLE, AndroidSerialTransport (Classic/USB)
  link/                   HsfzLink, ThorLink, ElmIsoTpLink, SimLink → DiagnosticLink.request(ecu, payload)
  protocol/               UDS codec, NRC decoding, 0x78 pending, keepalive scheduler, command queue
  domain/                 session machine (XState), ModuleRegistry, PresetRunner, effects
  simulator/              SimulatedVehicle (data-driven, fault injection)
  data/generated/         codegen output (do not edit)
  stores/                 Zustand stores (favourites, presets, settings)
  ui/                     gluestack theme, shared components (Tile, TileBackground, Section…)
  features/               screen-level components per feature
  i18n/                   en.json, pl.json
data/ecu/         F-series ECU source data (tracked)
scripts/gen-data.ts       codegen
e2e/                      Maestro flows
```

Session machine: `idle → connecting → identifying → ready ⇄ running → restoring → disconnected | error` (plus `reconnecting`).

## Safety policy

1. Forced control is always undone: off for every touched element → return-control → `10 01`. Runs on stop, completion, error, disconnect, and app backgrounding.
2. App going to background stops and restores immediately (iOS suspends sockets/BLE).
3. Identification fails closed: no known F module answering `22 F1 50` → presets locked with explanation.
4. Limits: 90 s per one-shot run or loop cycle; explicitly chosen Hold and Loop presets run until Stop, with restoration on background/disconnect/error. Light blocks can apply state without a delay; timed steps have a 50 ms minimum; command rate throttled to the adapter's measured RTT.
5. Error UX tiers: inline tile error (shake + red edge + reason, e.g. NRC 0x22 "stop the car / ignition on") → toast (transient) → full-screen state (adapter unreachable, Bluetooth off/denied, car not responding, connection lost while running).
6. Auto-reconnect: 3 attempts with backoff; if anything was under forced control, restore immediately after reconnect.

## Security

- Preset import: zod strict schema, size limits, unknown keys rejected, elements must exist.
- ENET/Thor host limited to private and link-local IPv4 ranges.
- Diagnostic recording is opt-in in release builds (Settings → Diagnostics), local and bounded to 300 in-memory entries. Development builds start with recording enabled. Copying is explicit and omits the VIN; no automatic upload.
- Sentry (`@sentry/react-native`) is the only network use: user-initiated problem reports (Home bug button) plus crash reports, with no other analytics. Enabled only when `EXPO_PUBLIC_SENTRY_DSN` is set; `sendDefaultPii` off, no tracing or replay, VINs and adapter hosts/IPs scrubbed in `beforeSend`/breadcrumbs/attachment. App Privacy must declare crash data and user content (feedback and diagnostic log).
- BLE connects only to devices exposing known adapter service UUIDs.
- Pinned dependencies, `npm audit --omit=dev --audit-level=critical` in CI (remaining highs are transitive in the Expo build toolchain, not shipped code).

## Known protocol uncertainties

- Nothing has been verified on a real car or adapter (except vendor claim for `2E D5 42 00 05 00 64`).
- FRM3 identity bytes `62 F1 50 0F 10 D0` medium confidence; FRM3 has no return-control (rely on per-light off + `10 01`; `2F 01 <ch> 00` unverified).
- Whether `2F 45 01 00 FE` cancels `2E D5 42` aggregate writes; meaning of the D542 time field.
- `ATFCSD` argument order (medium confidence); Thor adapter init/firmware behaviour.
- Keepalive `3E FF` vs `3E 80` semantics and cadence; whether the KOMBI routine `31 01 F0 12 01 FC 21` is required.
- IO-control response matcher should check channel, not only DID (prototype weakness); generated `expectedResponsePrefix` covers service and DID only because the data does not say whether the channel is echoed.
- LHM2_L/R: the channel routine writes a 14-field record but each mapping row names one field, so no LHM2 element is generated (FLE02 covers F20 headlights). FRM3 `SL_I_L` has an empty channel list (`tailInnerLeft` not generated); FRM3 `BL_L_2/R_2` and `ABBL_L/R` have no channels (not generated).
- Pack actions contain no timing: steps are ordered ticks and the runner picks the interval. Toggle ON/OFF actions are merged into one effect with `offSteps`.
- FLE02 `STOP_ROUTINE` (`31 02 A5 43`) is kept as a command only; unverified that it stops every LED routine, so it is not treated as return control. COMMUNICATION_OFF (`28 02 01`) is required by headlight LED effects (`silenceCommunication`) and must be restored with `28 00 03`.
- F32 has no row in the identification table (FEM_20 `0F16B0` is listed under F20), so chassis-to-module hints are sparse; identification relies on `22 F1 50`.
- F10 `positionLeft`/`positionRight` alias `daytimeLeft`/`daytimeRight` (same channels); F10 has no `ambient`, only `ambient1`/`ambient2`.
- IO-control response matcher: for FEM-style `2F 45 01 03 <ch> <st>` the channel is compared only when the ECU echoes it (a bare `6F 45 01 03` is accepted; the reply layout of FEM_20 is unverified). FRM3-style requests carry the channel in the DID, which is always compared.
- Timeout policy: any request timeout fails the link (late replies cannot be told apart from new ones); the session layer must reconnect and restore. Exception: identification probes (`probe: true`) on HSFZ, Thor and SimLink only drop the pending request, because replies are matched by source address; ELM keeps the fail-and-reopen behaviour (its output cannot be attributed).
- ELM: `NO DATA` after the last frame is surfaced as `AdapterError('no-data')`; 0x78 on ELM is followed with `ATMA` monitoring (unverified on hardware); `ATH1` frame lines are assumed to look like `640F1...` (id + data, no spaces).
- ENET discovery packet (type `0x11`) and `DIAGADR..BMWMAC..BMWVIN..` announcement format are from memory of the ENET spec, not from the app evidence.
- ENET discovery UDP socket: `react-native-udp` is unmaintained for Expo SDK 57, so a local Expo module `modules/bimmerdisco-udp` (BSD sockets on iOS, `DatagramSocket` on Android) provides it, wrapped by `src/transport/UdpSocket.ts` and wired in `native-deps.ts`. UNVERIFIED on a real car/device: (1) iOS 14+ documents the restricted `com.apple.developer.networking.multicast` entitlement (Apple approval needed) for sending/receiving broadcast and multicast; Apple's Local Network FAQ says enforcement was incomplete on iOS 14/15 but should be correct from iOS 16, and reports exist of broadcast replies being dropped on 14.5+ even with the entitlement. The entitlement is NOT in `app.json`. If discovery finds nothing on a real iPhone, request the entitlement or fall back to the manual ENET host field (a USB-C ENET gateway is always at a 169.254.x.x address, so unicast to a known IP always works). (2) The wrapper also sends the request to every interface directed-broadcast address (e.g. 192.168.1.255) in addition to `169.254.255.255`, for Wi-Fi gateways. (3) Car test 2026-10-13: auto-discovery found nothing on a real iPhone + USB-C ENET, manually typed IP connected fine. PARKED until the multicast entitlement is requested; "Try the last working IP first" is implemented (2026-10-14): `lastEnetHost` is saved once a session is ready and tried before discovery when the ENET field is empty, so discovery is only a first-connect problem. Unchecked alternatives: binding the broadcast to the 169.254 interface (`IP_BOUND_IF`) and trying `169.254.0.12` first. (4) Android needs no `MulticastLock` (replies are unicast) and no new permission; not compiled or run yet because no Android SDK was available when written.
- Probing addresses of modules the car does not have times out (700 ms each) without failing the link on HSFZ/Thor; a real gateway may answer absent ECUs with an error frame instead, which would be faster. Unverified. A late `62 F1 50` from an absent-then-answering ECU is discarded by the source-address filter. Thor default host 192.168.0.10 is taken from the vLinker log string, not verified for Thor (port 23 is from the app constructor).
- Restoring after a lost link assumes the ECU session may or may not have timed out on its own: the restore re-enters `10 03`, switches every touched element off, sends return control, `28 00 03` if silenced and `10 01`. Whether an ECU accepts `10 03` + IO control immediately after its S3 timer expired is unverified.
- Which modules should receive `28 02 01` is inferred (only modules serving the headlight-LED elements of the run); the app evidence lists `COMMUNICATION_OFF` for the LHM groups.
- Cleanup counts any rejected step (including a rejected element off or return control) as an unconfirmed restore, even if `10 01` was acknowledged; this is deliberately conservative and may show a false "lights may be on" on a real car.
- The preset `color` is validated as a lower-camel token key and `icon` as a PascalCase Phosphor name; the real token list lives in the UI layer (M6) and should be enforced there.
- `AppState` `inactive` is ignored (only `background` stops and restores) because the app switcher and control centre do not suspend sockets; the UI layer must supply `AppStateSource` from `react-native` `AppState`.
- `react-native-ble-plx` 3.5.1 is an old-architecture bridge module; confirm it runs under RN 0.86 (interop layer) on a dev build before M7.
- F32 with LED headlights: whether FLE02_L/R are detected by `22 F1 50` on this car is unverified (check the debug log line `identified ...` at the next test; if they are missing, the per-side headlight rule will not trigger). The FLE02 segment routine (`31 01 A5 43 FF`, `headlight_flash.leftHeadlight`) is unverified on the car. FEM `2E D5 42 00 0C 00 64` (brake) is ignored on an F32 that has REM_20; the substitution rule assumes any REM_20 car behaves the same, and the per-side headlight rule assumes any FLE02 car does.
